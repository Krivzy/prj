# Awwwards Creative Web Developer

Подготовь выразительный, работоспособный интерфейс по задаче пользователя. Название описывает творческое направление, а не обещание награды или FPS. Ответы и проектные решения объясняй на русском; имена API оставляй на английском.

## Сначала определить границы

Изучи структуру проекта, lockfile, маршруты, incumbent UI, scripts, тесты, требования и AGENTS.md. Различай refinement и redesign: при refinement сохраняй визуальную идентичность и рабочие сценарии. В новом проекте установи аудиторию, ключевое действие, тип контента, реальные assets и ограничения устройства. Не мигрируй существующую архитектуру только ради привычного стека. Критические неизвестные уточняй, остальные обозначай как предположения и продолжай.

До сложного UI сформулируй короткий visual brief: идея и настроение, композиционный приём, типографическая пара/система, цветовые роли, spacing/grid, правила движения и мобильный вариант. Согласуй его с реальным брендом и содержимым. Фиксируй полезные решения в существующем DESIGN.md либо подходящем файле проекта; не создавай документацию без необходимости. Не выдумывай отзывы, метрики и product claims.

## Подключать модуль под конкретное решение

Прочитай [routing.md](references/routing.md), когда требуется выбрать specialist. Загружай только SKILL.md выбранных навыков и только относящиеся к задаче references. Наличие этой системы не означает необходимость прочитать её целиком. Путь специалиста — sibling folder в глобальном skills; если отсутствует, проверь текущий каталог skills и доступные инструменты, затем честно обозначь fallback.

Технологию выбирай по сложности эффекта:

- CSS transition/keyframes: hover, focus, простые reveals, несколько состояний. Проверяй поддержку advanced CSS в целевых браузерах.
- Motion: React gestures, springs, presence, layout/shared-layout и локальные microinteractions.
- GSAP: режиссируемые timelines, ScrollTrigger/pinning, сложные последовательности, SVG и FLIP.
- Lenis: только оправданная smooth-scroll композиция; native scroll остаётся исходным вариантом.
- Three.js/R3F: пространственное представление, интерактивный продукт или содержательная 3D-сцена; не добавляй canvas ради декоративного тренда.
- GLSL: эффект, который проще и дешевле считать GPU, чем DOM, с fallback и проверенным budget.
- 21st.dev: поиск подходящего компонента с оценкой license, dependencies, a11y и эстетики; не импортировать весь шаблон автоматически.

Один владелец DOM-property или canvas transform. Разделяй эффекты wrapper layers, если нужны GSAP и Motion. У scroll есть один владелец. У каждого render loop или связанной композиции есть определённый источник времени: не дублируй Lenis RAF или R3F render loop, но независимые runtime могут сосуществовать с явным контрактом обмена progress. У каждого эффекта есть start/stop, cleanup и reduced-motion вариант. WebGL и анимации не должны прятать существенный текст, блокировать ввод или заменять доступную навигацию.

## Архитектура и реализация

Отдели content/data, domain logic, layout, компоненты и effect controllers. Для Next.js App Router сохраняй Server Components по умолчанию и узкие client islands для интерактивности. В существующем Pages Router используй его реальные возможности, не мигрируй router ради skill. Проверяй права и вход на сервере при любой архитектуре. Обсуди auth/realtime/инфраструктуру по фактической задаче. Используй текущие совместимые stable версии, проверив docs и peerDependencies; не навязывай версии, записанные в старом примере skill.

Начни с полноценного semantic static UI и основных сценариев. Добавляй эффекты после работающей композиции. Loading/error/empty/disabled/success — части готового продукта. Подстрой движение, плотность и качество render под touch/viewport/устройство; не своди мобильную адаптацию к уменьшению desktop. Не ставь custom cursor или smooth scroll по умолчанию. Lazy-load тяжёлую сцену; резервируй её площадь и покажи meaningful fallback.

## Приёмка по наблюдаемым результатам

Используй scripts проекта: подходящие lint/typecheck/tests/build. Затем открой настоящий UI и проверь основной путь пользователя, формы, навигацию, ошибки JS/network и состояния. Для визуальной задачи подключи visual-quality-assurance-expert: viewport, screenshots, композиция, контент, spacing, focus, анимация и её отключение. Для производительности подключи performance/core-web-vitals и сравни измерения в одинаковых условиях. При 3D проверь отсутствие WebGL, потерю context, quality downgrade и unmount.

Исправь обнаруженные дефекты и повтори затронутые проверки. Добавляй regression tests для важных сценариев и исправленных ошибок, а не тесты, повторяющие implementation. Не называй результат готовым по одному build. Если доступен только код, не выдавай гипотезы о визуальном качестве/FPS за результаты браузерного измерения. Если проверка заблокирована, укажи точное ограничение и минимальный следующий шаг.

## Что передать пользователю

Объясни результат, выбранную визуальную идею и важные технологические решения, изменённые файлы, выполненные проверки и реальные ограничения. Для сложного проекта сохрани понятные launch/check commands и зависимости без credentials. Deploy, покупка assets и внешняя публикация следуют авторизации текущей задачи; skill не выдаёт дополнительных разрешений. Правила Obsidian/GitHub применяй из действующих AGENTS.md, не из копии заметки.
