# MCC 0.10 и MCC Core 0.2

Версия 0.10 добавляет первый запуск с настоящим Minecraft владельцем, временные режимы доступа панели и подготовку MCC Core из самой панели. MCC Core 0.2 включает изменения движка закреплённого Paper 26.3; его скорость относительно Purpur/Pufferfish должна подтверждаться отдельными одинаковыми нагрузочными измерениями.

## Первый запуск и доступ

Чистая установка не создаёт публичный аккаунт admin/admin. Персональную одноразовую ссылку получает настоящий онлайн-игрок с OP или `mcc.setup`. Ник и UUID подтверждает Bukkit; браузер их не назначает. Ссылка действует десять минут, capability передаётся в URL fragment и потребляется при claim. Setup cookie, Origin и CSRF защищают запросы мастера. Право и онлайн-состояние повторно проверяются перед созданием единственного Owner, в том числе после вычисления Argon2 hash.

Четыре шага позволяют выбрать пароль, пресет ядра, режим панели и просмотреть итоговый план. В пробной боковой навигации подпись занимает отдельную flex-область; SVG-замок размером 14 px имеет зарезервированное место справа. Эта source-правка устраняет причину наложения текста и замка; её состояние отдельно проверено в итоговом браузере, как описано ниже. Пробная версия оставляет обзор с текущими метриками, консоль, чат и настройки. Сервер применяет ограничения на HTTP API, WebSocket и уже поставленные в очередь действия; соответствующие закрытые модули прекращают фоновую работу. Owner recovery API резервных копий остаётся доступным. Временная полная версия локальна; удалённый сервис лицензирования не реализован, произвольные лицензионные ключи отклоняются. Подробности: [ONBOARDING.md](ONBOARDING.md).

Действующие изменённые аккаунты и аудит сохраняются. Только известный единственный legacy Owner с исходным публичным паролем проходит тот же мастер заново. Это не автоматическое удаление всех прежних пользователей и не создание нового пароля оператором развёртывания.

## Порт и удалённая первая ссылка

Новые установки и fallback отсутствующего `web.port` используют 8123. Обновление сохраняет явно настроенные порты: Main 8080, отдельные QA порты и allocation хостинга не переписываются. MCC не выбирает запасной порт автоматически и не разделяет один listener с Dynmap. Перед первой персональной ссылкой на удалённом сервере задайте `web.public-origin` с настоящим адресом панели/HTTPS reverse proxy и выполните обычный перезапуск: при пустом origin ссылка использует `http://localhost:<port>`, публичный hostname не угадывается. [Порты хостинга и конфликт с Dynmap](HOSTING-PORT.md), [настройки безопасности](../SECURITY.md).

## MCC Core 0.2

Основа — Paper 26.3 build 169 BETA, source commit `46d4834e8e2ec4af9dcfa028076fb16dfb8a3911`. Foundation: 55 980 330 байт, SHA-256 `86c96263ba9a6257cc8b03e8e8fd8f90ee03fedb396918ed1fa1f74ebe196223`, patchset SHA-256 `3d42ace4d8f3a14bb7765cb173da0bcd06aa7a6533bd33e4e8892a50d0ca3c6f`.

Изменения движка ограничивают scratch-аллокации генерации руды, ускоряют обход NBT и кодирование long arrays, упрощают снимки heightmaps и удаляют лишние поля palette storage. Сохраняются основной игровой поток и публичные Bukkit/Paper контракты; штатные workers генерации/IO Paper продолжают работать. MCC не переносит AI, сущности или callbacks плагинов на произвольные потоки. Это не обещание полной идентичности Mojang Vanilla и совместимости любой версии любого плагина.

Core проверяет точную пару MCC/Core до загрузки миров. После bind веб-сервера устанавливается живой CoreBridge; потеря панели вызывает публичный штатный `Bukkit.shutdown()` с сохранением. Закрытие браузера не прекращает серверную панель. После обновления MCC Core нужно подготовить заново, поскольку привязка использует SHA-256 MCC JAR.

Подготовка извлекает проверенную foundation локально из MCC JAR. Рабочий server JAR заменяется только при следующем штатном запуске, после завершения прежней JVM и создания проверенной копии. Для обычного Paper/Purpur открытие панели не распаковывает 56 MB foundation и не загружает её целиком в heap. Режим `vanilla-throughput` сохраняет текущие distances и активность сущностей; значение autosave 24 чанка за тик уже является обычным значением Paper и само по себе не доказывает выигрыш MCC. [Установка, pairing и откат](MCC-CORE.md), [восстановление движка из исходников](../core-engine/README.md).

## Учёт установленного MCC JAR

Bundled foundation увеличила собственный MCC JAR до 91.4 MB. Общий прежний предел 64 MiB для inventory приводил к HTTP 500 при `/api/plugins/manage`. Проверка существующих локальных JAR теперь допускает 128 MiB только для точного сочетания `name: MinecraftControlCenter` и `main: dev.mcc.MccPlugin`; остальные JAR сохраняют 64 MiB. Этот предел используется согласованно в inventory и хешировании. Загрузки каталога остаются ограничены 64 MiB; ZIP сохраняет пределы 64 MiB на entry, 256 MiB суммарно и 25 000 entries. Пять регрессий этой причины прошли в общей source-сборке; свежая native-пара также прошла управление inventory/JAR на обоих стендах.

## Фоновые очереди и остановка карты

LogTail отправляет за один pulse не больше четырёх immutable console batches: до 16 строк и 24 576 байт JSON UTF-8 массива в каждой. Отдельное сообщение ограничено 4096 UTF-16 code units и 16 384 байт JSON, без разрыва surrogate pair. Хранится не больше 65 536 сырых байт, 32 768 байт незавершённой строки и одной отложенной записи; история сохраняет последние 500 строк. Realtime queue остаётся 32. Начальное окно 16 KiB и catch-up окно 64 KiB сохраняются; срезанный фрагмент физической строки пропускается. Одиннадцать новых LogTail regression cases и две прежние Realtime проверки прошли без skips: порядок 151 startup rows, split UTF-8/CRLF, незавершённая строка и redaction, append/history, truncate/меньшая замена, временное отсутствие файла и tail-skip. Равная или большая замена файла не заявлена как новая поддержанная rotation. Focused receipt SHA-256 `bfb9e76b0380d34755dc25a429e95b66d56e4eb390db13882468b5bcb6413cbd`.

SavedImageMap сохраняет финальный manifest перед удалением recovery marker и публикует `ready` только после обеих операций. `close()` прерывает worker и ждёт его фактического завершения до освобождения cache resources; ожидание ограничено десятью секундами, при превышении возвращается ошибка. Две новые deterministic проверки удерживают реальную сериализацию и активный worker: `ready` не виден преждевременно, а прежний worker не может после успешного close менять marker следующего поколения. Все 20 focused SavedImageMap тестов прошли без ошибок и skips; receipt SHA-256 `8197ff8631ae69232cddc31130cd153c34a4ab2ddd46045a383d8bb465f43419`. Это source-проверки; отдельные browser report и свежая полная native-пара текущего JAR завершены в описанной ниже области.

## Сохранение и восстановление

Перед изменениями подтверждена закрытая копия MCC 0.9: 4611 файлов, 87 743 022 байта. Это копия исходников, JAR и конфигурации; она не подменяет полную offline-копию миров и SQLite после штатной остановки. В начале задачи Main работал на прежней MCC 0.9. Итоговое обновление Main выполнено после отдельной закрытой offline-копии 10 109 файлов / 485 425 076 байт с проверкой трёх SQLite баз; исходный snapshot не заменяет эту копию или актуальное liveness-доказательство.

Исходники, patchset движка, собственные helpers, tests, build scripts и license notices предназначены для публичного снимка. Пароли, capabilities, SQLite базы, миры, резервные копии, generated Minecraft source, игровые PNG и JAR-бинарники в source repository не публикуются. Последний подтверждённый commit прежней MCC 0.9 сохраняется как история; новый commit 0.10 фиксируется только после проверки опубликованного ref и точных байтов файлов.

Сборка и запуск: [README](../README.md). Откат MCC выполняется после normal stop возвратом прежнего проверенного MCC JAR. Откат установленного Core также возвращает прежний server JAR и, если мигрировал managed Purpur profile, отдельный `previous-kernel-profile.json`. Миры и базы автоматически не перематываются.
