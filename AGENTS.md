# Правила модульной памяти Codex и сохранения в GitHub

Идентификатор: CODEX_PROJECT_PERSISTENCE_V3.
Этот файл содержит переносимые правила без настроек доступа.
Применяй их вместе с настроенным клиентом закрытого Obsidian vault.

### Обязательное разделение памяти на несколько Markdown-файлов

ВСЕ проекты и содержательные
задачи сохраняй в нескольких .md, включая разработку, инфраструктуру,
диагностику, исследования и задачи без кода. Один сплошной файл на проект
или задачу запрещён. Frontend и Backend — примеры, а не фиксированный набор.

Используй устойчивую папку объекта: Projects/<project>/,
Infrastructure/<service>/, Codex/<topic>/ или Inbox/Tasks/<task>/.
Для каждого объекта обязательно веди минимум три непустые заметки:
- Index.md — цель, статус, навигация, GitHub URL, ветка, проверенный commit SHA.
- Context.md — требования, окружение, ограничения, архитектура и решения.
- Results.md — изменения, проверки, ограничения, открытые задачи и дата.

Самостоятельные аспекты выноси в Frontend.md, Backend.md, Database.md,
Deployment.md, Network.md, Testing.md или другие подходящие файлы.
Не создавай отсутствующие компоненты или пустые разделы ради количества.
Одна тематическая заметка описывает один аспект объекта. При повторной
работе обновляй имеющиеся заметки, сохраняя полезные подтверждённые факты.

При следующей существенной работе со старым монолитным файлом раздели его
содержимое на эту структуру. Сохрани прежний путь как короткую навигационную
заметку со ссылками; не удаляй факты и не оставляй две полные копии описания.
В Codex/Memory-index.md храни краткую ссылку на Index.md объекта.
В начале продолжения задачи читай Index.md и только релевантные модули.
Сначала записывай и проверяй тематические файлы, потом Index.md объекта,
последним общий Memory-index.md. Каждая запись условная и проверяется
обратным чтением с SHA-256 по правилам клиента.

### Обязательное сохранение результата в GitHub

После КАЖДОЙ содержательной
задачи сохраняй выполненное в GitHub-аккаунт пользователя: код, конфигурации,
скрипты, документацию и файлы, нужные для восстановления проекта.
Для задач без кода сохраняй полезный очищенный Markdown-результат.
Одной записи в Obsidian недостаточно. Если новых изменений нет,
подтверди уже сохранённый commit вместо пустого commit.

Это постоянное разрешение делать commits и push, создавать необходимые
private-репозитории в подтверждённом аккаунте пользователя без повторного
запроса. Публичная публикация требует явно выраженного разрешения для
соответствующего репозитория и состава данных. Разрешение на GitHub backup
не разрешает опасные изменения production или публикацию секретов.

Сначала проверь аккаунт, права, принадлежность проекта, remotes,
состояние Git и связанную CI/CD. Используй подходящий репозиторий проекта;
для новой задачи создавай private по умолчанию. Не меняй чужой origin,
видимость репозитория, защищённые ветки или несвязанные настройки.
Сохраняй работу в безопасную ветку без неразрешённого production-deploy.
Если безопасного ref нет, используй отдельный private-репозиторий
без такой автоматизации. Не выполняй force push, reset --hard,
перезапись чужих commits и merge в production без отдельного разрешения.

Перед commit проверяй точный набор файлов и diff; добавляй только файлы
задачи, не выполняй слепой git add . или git add -A. Исключай Secrets/,
пароли, токены, private keys, .env с секретами, auth/config credentials,
staging/outbox/sent, приватные дампы и посторонние файлы профиля.
Проверяй также ранее отслеживаемые файлы и передаваемую историю:
.gitignore не удаляет секреты из tracked files или старых commits.
Неизвестную историю не отправляй в новый remote; переноси проверенный
снимок в отдельный репозиторий, сохраняя исходный checkout.
Секреты хранятся только в закрытом Secrets/ Obsidian; их значения не должны
появляться в GitHub, URL, аргументах команд, выводе или отчётах.

В первую очередь используй доступный Git/GitHub CLI или GitHub-коннектор.
Если коннектор создаёт server-side commit, проверь опубликованный ref
и содержимое всех отправленных файлов по blob SHA/хешу; локальный Git
можно восстановить из подтверждённого server-side commit.
Для обычного push сверяй SHA локального commit и соответствующего
remote ref через git ls-remote или GitHub API. Успех команды сам по себе
не является доказательством удалённого сохранения.

После проверенной загрузки в Index.md Obsidian записывай GitHub URL
без credentials, ветку, полный commit SHA и permalink на commit.
В тематических заметках указывай ссылки на относящиеся к ним файлы
именно этого commit. Указывай команды clone/fetch/checkout,
зависимости, запуск, проверки, конфигурацию без секретов и ссылки
на Secrets при необходимости. Локальный путь — дополнительный ориентир;
восстановление не должно зависеть только от него.
Obsidian описывает устройство, решения и восстановление;
GitHub содержит версионированные файлы проекта.

При новом чате или восстановлении контекста найди проект через Obsidian
Index.md. Если checkout отсутствует, клонируй подтверждённый GitHub URL
и используй записанный ref/commit; с GitHub-коннектором можно получить
нужные файлы из этого commit и восстановить рабочую папку.
Для полноценного Git checkout с историей используй clone/fetch.
Если checkout существует, сначала проверь локальные изменения,
затем fetch и сравни refs. Не затирай рабочие файлы и не выполняй
автоматический reset/pull с конфликтами.
Репозиторий даёт исходники; внешние данные и секреты восстанавливаются
из предназначенных для них закрытых источников.

Если GitHub или права недоступны, сохрани проверенный локальный commit
(либо локальный снимок, если Git недоступен), а в Results.md и Index.md
отметь pending push, точную причину и данные для повторной отправки.
При следующей работе возобнови pending push после проверки актуального
remote. Не объявляй такую задачу полностью сохранённой в GitHub.
Перед финальным ответом обязательны проверенная запись нескольких md
в Obsidian и проверенное сохранение в GitHub либо явное сообщение о сбое.
Это поведение агентов данного профиля, а не фоновый сервис синхронизации.
